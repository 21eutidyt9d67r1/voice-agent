# Voice Agent: keep callers informed during slow tools

Demonstrate a slow, client-executed order lookup without leaving the caller in
silence. The Agent says it will check, invokes a simulated tool, and generates
one extra spoken reminder if the tool is still pending after six seconds.
It then speaks the tool result. **All speech is generated by the Voice Agent;
the application does not call a TTS service or play a canned reminder.**

## Two Voice Agent modes

| `--model` | Speech path |
| --- | --- |
| `gpt-realtime` (default) | Realtime audio model with the Agent's configured Azure Speech output voice; Whisper input transcripts. |
| `gpt-5.4` | Azure Speech recognition (`azure-speech`) -> GPT-5.4 -> Azure Speech synthesis. |

Both create a managed **`kind: voice` Foundry Agent** and connect with
`AIProjectClient.beta.voice_agents.realtime.connect(agent_name=...)`.
This is not a direct Voice Live sample. Use a Project enabled for Voice Agents
and your selected managed model; the sample does not provision a Project or
fall back to another model. Region support and processing scopes must be
checked for your Project and model.

The lookup tool, `check_demo_order({"order_id": "DEMO-123"})`, is a read-only
simulation. It sleeps for a configurable delay and returns `status: shipped`.
It does not connect to an order system or change customer data.

## Run

Requires Python 3.11+, an eligible Foundry Project, and Agent data-plane
permissions. From the repository root, in PowerShell:

```powershell
python -m venv samples\long_tool_wait\.venv
samples\long_tool_wait\.venv\Scripts\python.exe -m pip install -r samples\long_tool_wait\requirements.txt
az login
$env:AZURE_VOICE_AGENTS_ENDPOINT = "https://<account>.services.ai.azure.com/api/projects/<project>"
```

Install the optional microphone dependency; Linux/macOS also need PortAudio:

```powershell
samples\long_tool_wait\.venv\Scripts\python.exe -m pip install "PyAudio>=0.2.14,<0.3"

# Speech-to-text / GPT-5.4 / text-to-speech pipeline.
samples\long_tool_wait\.venv\Scripts\python.exe samples\long_tool_wait\long_tool_wait.py --model gpt-5.4
```

Ask: **"Check the status of order DEMO-123."** Use a headset to avoid echo.
Talk over a reply to interrupt; Ctrl+C exits. Talking does **not** cancel the
lookup: ask "Why is it taking so long? Please keep checking." To abandon it,
say "Cancel the lookup." New microphone turns wait for
input transcription before requesting a model response, including in pipeline
mode.

## How the reminder works

1. A completed function-arguments event starts the tool asynchronously. The
   receive loop stays active. A function call in `response.done` is also
   accepted if no earlier arguments event was received.
2. After the tool-calling response's `response.done`, start the six-second timer.
   A tool that already finished skips the timer.
3. If the tool finishes before the timer, cancel the timer, submit the matching
   `function_call_output`, and request one normal response.
4. If the timer expires first, request one out-of-band spoken reminder.
5. If the tool finishes during the reminder, hold its output until that
   reminder's `response.done`. Then submit the output and request one normal
   response. If the reminder finishes first, continue awaiting the tool without
   scheduling more reminders.

The Voice Agent SDK payload uses **`output_modalities`**, not the dated Voice
Live `modalities` field:

```python
VoiceAgentResponseCreateParams({
    "conversation": "none",
    "input": [],
    "output_modalities": ["text", "audio"],
    "tool_choice": "none",
    "interim_response": None,
    "metadata": {
        "purpose": "tool_wait_reminder",
        "request": "<unique-request-id>",
    },
    "instructions": (
        "Say only: This is taking a little longer. I'm still checking. "
        "Do not add anything else."
    ),
})
```

`conversation: none` excludes the reminder from conversation history;
`input: []` isolates it from the unfinished function call, and `tool_choice:
none` disallows another tool call. The session's configured voice is reused.
The final result response uses the normal conversation, with further tool calls
disabled so "keep checking" cannot accidentally launch another lookup.

### Caller speech while a lookup is pending

Caller speech clears queued playback, cancels an active reply, and cancels the
reminder timer, **but leaves the asynchronous lookup running**. After the
caller's transcript arrives, the Agent answers through another out-of-band
response isolated from the unfinished function call. It can answer a question
without waiting for the tool. These short side replies do not enter the default
conversation history; user utterances still do.

The pending-lookup reply selects between `cancel_demo_lookup({})` and
`get_demo_lookup_status({})`. It requires a tool decision before answering:
cancel for an explicit stop request, or check status without cancelling for
questions and "please keep checking." This prevents a spoken "cancelled"
without executing cancellation. All functions are registered on the Agent
for pipeline compatibility; per-response tool filtering is not treated as an
authorization boundary.
The local controller only permits status/cancellation through this
pending-lookup path; reminder and final responses use `tool_choice: "none"`.
The local handler
cancels the read-only task, confirms cancellation using an inline out-of-band
tool result, and resolves the original lookup's `call_id` with a cancelled
output. A lookup that already finished cannot be claimed as cancelled.

If the lookup finishes while a side reply is being generated, result delivery
waits for that reply's `response.done`. The controller rejects new lookups in side
replies, so only one lookup can be pending. The interrupted reminder timer is
not restarted for that lookup.

A single controller owns scheduling. The socket reader, tool task, and timer
enqueue events; only the controller sends response requests and tool outputs.
`response.created` metadata identifies the requested response, and its ID
correlates audio and `response.done`. Only one response is in flight at a time.

**Generation completion is not playback completion.** Reminder and final audio
share a bounded FIFO PCM buffer. The final audio plays after queued reminder
audio instead of overlapping it. Barge-in clears this buffer, including partial
chunks, and discards late audio from the cancelled response. Already submitted
device audio cannot be recalled; microphone mode uses 50 ms chunks.

## Try the timing paths

| Options | Expected behavior |
| --- | --- |
| Defaults: `--tool-delay 10 --reminder-after 6` | One reminder if still pending six seconds after the first response completes, then the result. |
| `--tool-delay 0` | Fast tool, no extra reminder. |
| `--tool-delay 7 --reminder-after 6` | May finish during reminder generation; output waits for its completion. Exact timing depends on service latency. |
| `--tool-delay 40 --tool-timeout 8` | Explicit timeout failure; never a fabricated successful result. |

All timing options accept finite values from 0 through 120 seconds. The tool
timeout defaults to 30 seconds. Text smoke tests have a 180-second overall
limit, and individual responses have a 120-second limit.

Caller speech targets any active response for cancellation; new responses wait
for its completion/cancellation and the next caller transcript. A function whose
generation was cancelled before complete arguments arrived is not executed and
receives an explicit cancelled output. A lookup already started from complete
arguments keeps running unless explicitly cancelled. For real side-effecting tools, define cancellation
and idempotency separately: cancelling a task does not undo external actions.
This terminal sample does not truncate previously generated normal replies to a
hardware-measured playback position; out-of-band reminders never enter history.

Unknown tools and invalid arguments return explicit failures. Parallel calls,
unmatched metadata, generation failures, unexpected cancellation errors, audio
loss/overflow, and disconnects fail visibly and clean up background tasks.

Each run creates and retains an Agent and prints its Agent/session IDs.
Conversation/audio persistence is disabled (`store: false`), but normal
conversation context remains available for the live session. Azure usage is
billable; use nonsensitive test requests.
